# swift-java full adoption — design

Replace every hand-written `@_cdecl` JNI entry point in
`SheetMusicAndroidJNI` with swift-java's jextract-generated bridges,
collapse the PoC module `SheetMusicAndroidJNISwiftJava` into the main
module, and let the official swift-java toolchain own the Swift ↔ Kotlin
boundary going forward.

## Background

The Android port currently has 23 hand-written `@_cdecl` functions across
`Sources/SheetMusicAndroidJNI/` (Audio 16 + Score/Layout 7). Each one is
a thin wrapper that does:

1. `GetByteArrayRegion` / `NewByteArray` ceremony to move bytes between
   `jbyteArray` and Swift `Data`,
2. payload decode via a hand-written codec,
3. call into pure-Swift logic,
4. payload encode + return.

The byte-marshalling layer alone is ~140 lines repeated across 14 sites
(`AudioMidiBridge.swift` lines 66–97 + the per-bridge `@_cdecl`
functions). Kotlin-side `external fun` declarations and packaging into
`io.github.jiyimeta.sheetmusic.SheetMusicJNI` /
`io.github.jiyimeta.sheetmusic.audio.jni.SheetMusicAudioJNI` mirror this
by hand.

We've already validated swift-java 0.3.0 in PoC form via
`SheetMusicAndroidJNISwiftJava` (3 functions: ping / echo /
gmInstrumentList) with `mode: "jni"` and the `JExtractSwiftPlugin`. The
generated Kotlin landed in `io.github.jiyimeta.sheetmusic.swiftjava` and
was wired into `Examples/Android/` via a hand-written `SwiftJavaFacade.kt`
wrapper.

The PoC proves the toolchain works end-to-end at the
3-function scale. This spec promotes it to all 23 entry points.

## Goal

After this work:

- Zero `@_cdecl` functions in `Sources/SheetMusicAndroidJNI/`.
- One Swift target (`SheetMusicAndroidJNI`), no separate
  `SheetMusicAndroidJNISwiftJava`.
- All JNI bridging is generated by `JExtractSwiftPlugin`; the only
  hand-written Swift inside `SheetMusicAndroidJNI` is the public
  business-logic API jextract reflects into Kotlin.
- Kotlin callers (`Examples/Android/`, `SheetMusicAudioAndroid`,
  `SheetMusicAndroid` library tests) reach Swift via the swift-java
  generated classes directly — no hand-written `SheetMusicJNI` /
  `SheetMusicAudioJNI` facade class.

## Non-goals

- **Audio codec wire format changes.** Migrating the 12 audio codecs to
  `@WireFormat` is a separate spec (will be written after this one). The
  two pieces are independent: this spec only changes the JNI boundary,
  not the bytes that cross it.
- **`@WireFormatRandom` macro for SheetMusicZip.** Deferred indefinitely
  — pursued later as technical exploration, not part of this push.
- **JNI byte-marshalling helper consolidation.** Originally planned as a
  preparatory step; obsoleted by this spec since jextract removes those
  helpers entirely.
- **Performance regression coverage.** No byte-level regression test or
  benchmark. If perf degrades materially, that's a follow-up.

## Scope

In:

- Migrate all 23 `@_cdecl` functions to swift-java jextract bridges.
- Delete `Sources/SheetMusicAndroidJNISwiftJava/` (move `swift-java.config`
  into `Sources/SheetMusicAndroidJNI/`).
- Update `Package.swift` so `SheetMusicAndroidJNI` depends on
  `SwiftJava` and applies `JExtractSwiftPlugin`.
- Replace the hand-written `SheetMusicJNI` / `SheetMusicAudioJNI` Kotlin
  classes with calls into the jextract-generated Kotlin (whatever shape
  the tool emits — we adopt it as-is and update all call sites).
- Delete `SwiftJavaFacade.kt`; the Compose example calls jextract output
  directly.

Out:

- Audio codec internals (see Non-goals).
- ZIP wire format macro work.
- Apple-side build or any change outside `Sources/SheetMusicAndroidJNI`,
  `Android/`, and `Examples/Android/`.
- Maven artifact `groupId`/`artifactId` rename. The published
  `io.github.jiyimeta:sheet-music-{android,audio-android}` coordinates
  stay the same; only the Kotlin classes inside the AAR change shape.

## Migration order

Module-by-module, two commits / two verification rounds:

1. **Audio module (16 functions).** Migrate every `@_cdecl` in
   `AudioMidiBridge.swift`, `AudioMidiBridge+Render.swift`,
   `AudioMidiBridge+Timeline.swift`, and the Audio-namespaced entries in
   `JNISymbols.swift`. Update `SheetMusicAudioAndroid` and the
   Compose example's audio path. Verify, then commit.
2. **SheetMusic module (7 functions).** Migrate the Score/Layout entries
   in `JNISymbols.swift`, `CursorBridge.swift`, `LoopHighlightBridge.swift`.
   Update `SheetMusicAndroid` library and the Compose example's score
   path. Verify, then commit.

Each phase leaves the Compose example app working — at the boundary
between phases, the app still launches and renders, only the audio
subsystem switches under it.

## Technical risks (resolved during implementation)

These are unknowns we accept entering implementation. The plan should
front-load whichever experiment resolves each one:

- **`ScoreHandle` opaque pointer (jlong).** `nativeLoadScore` returns
  `jlong` and subsequent calls (`nativeReleaseScore`, `nativeScoreMetadata`,
  `nativeComputeLayout`, `nativeCursorFrame`, `nativeLoopHighlightRects`)
  pass it back. swift-java 0.3.0's jextract behaviour for pointer-shaped
  `Int64` values is unverified. Resolution: **migrate `nativeLoadScore`
  + `nativeReleaseScore` first within Phase 2 as a spike**. If jextract
  doesn't preserve pointer identity, fallback is a Swift-side handle table
  (`[Int64: Score]`) that hands out integer keys — same surface area for
  Kotlin, more bookkeeping in Swift. Cost ~50 lines either way.
- **ByteBuffer no-copy path.** Current code uses
  `GetByteArrayRegion` (copy). jextract may emit `byte[]` (copy-equivalent)
  or `ByteBuffer` (potential no-copy). Resolution: observe what the first
  Audio function emits, adopt it. If performance regresses noticeably in
  manual emulator testing, file follow-up; do not block this spec on it.
- **Build at scale.** `JExtractSwiftPlugin` worked for 3 functions. 23
  functions across multiple Swift files plus Gradle composite build may
  expose plugin caching, classpath, or generated-source layout issues.
  Resolution: completing Audio phase (16 functions, multiple files) is
  itself the validation; if the plugin can't scale, we know after
  Phase 1.
- **Kotlin package and class naming.** swift-java will emit classes into
  a package and a shape we don't yet control finely. Resolution: take
  what jextract emits, update all Kotlin call sites in the same commit.
  No facade layer.

## Verification

A phase is "done" when all of the following pass:

1. `swift test` — full host-platform Swift test suite green.
2. `./gradlew :SheetMusicAndroid:test :SheetMusicAudioAndroid:test` —
   Android library JVM unit tests green.
3. Compose example app (`Examples/Android/`) installed on Pixel 6 Pro
   API 36 emulator, manual smoke: MIDI playback audible, score scrolls
   with cursor.

After Phase 2 (SheetMusic migration), the same checks gate the final
commit.

## Open questions for the plan

The plan author should answer these during implementation, not before:

- Free function vs. `@JavaImplementation` class methods — what does the
  emitted Kotlin look most idiomatic as? Inspect what jextract emits for
  one Audio function before committing to a pattern for all 23.
- Where does `swift-java.config` live after the module collapse —
  `Sources/SheetMusicAndroidJNI/swift-java.config` or alongside
  `Package.swift`? Whichever the plugin requires.
- Does any of the 23 functions take or return a type that jextract can't
  represent (e.g., callbacks, function pointers, opaque structs)? Survey
  during plan-writing; flag any that need a special path.
