# Android ZIPFoundation cross-compile unblock — Implementation Plan

> **STATUS: SUPERSEDED (2026-05-19)** — Execution of this plan revealed two structural blockers that the spec did not anticipate:
> 1. `Archive(data:)` is unavailable on Android because the Swift Android SDK doesn't expose Bionic's `cookie_io_functions_t` / `fopencookie`. ZIPFoundation explicitly disables in-memory archives on Android (post-PR-#380 commits `bf30155` / `fc5a039`). Working around this in `swift-sheet-music` would require temp-file shims in MSCZReader / MSCZWriter / MXLReader.
> 2. Even with the in-memory shim, `CZLib`'s `pkgConfig: "zlib"` makes SwiftPM resolve the macOS-arm64 Homebrew `libz.a` on the host and inject `-L/opt/homebrew/opt/zlib/lib` into Android link commands, which `lld` rejects.
>
> Outcome: `Phase 1.5` was abandoned and the worktree was returned to Phase 1 state (`weichsel/ZIPFoundation 0.9.20`, `.mscz` / `.mxl` Android-unsupported). The `jiyimeta/ZIPFoundation` fork (branch `android-manifest-fix`, tag `pinned-do-not-delete` at commit `3219223`) was pushed but is no longer consumed; archive at convenience.
>
> Replacement direction: **Phase 1.6 — `SheetMusicZip` in-house module** (Swift ZIP container + platform DEFLATE: `Compression` framework on Apple, system `zlib` on Linux / Android). This avoids both blockers (no `fopencookie`, no `pkgConfig` host injection) and produces a long-lived asset independent of ZIPFoundation's maintenance trajectory. A future evolution can replace the platform DEFLATE backing with a pure-Swift implementation without changing the container or call sites.
>

- [ ] **Step 2: Write the dedent helper**

The mechanical edit on each file is "drop line 1 `#if`, drop final `#endif`, remove leading 4-space indent from every interior line". A small Python script handles all three files uniformly and fails loudly on shape surprises (per CLAUDE.md's "don't pipe multi-line scripts into interpreters via heredoc" rule, this is written to a file first and then run).

Use the `Write` tool to create `/tmp/strip-android-guard.py` with:

```python
#!/usr/bin/env python3
"""Strip `#if !os(Android)` ... `#endif` envelope and dedent interior by 4 spaces."""
import sys

path = sys.argv[1]
with open(path, "r", encoding="utf-8") as f:
    lines = f.readlines()

if not lines or lines[0].rstrip("\n") != "#if !os(Android)":
    print(f"error: {path}: line 1 is not `#if !os(Android)`", file=sys.stderr)
    sys.exit(1)
if lines[-1].rstrip("\n") != "#endif":
    print(f"error: {path}: last line is not `#endif`", file=sys.stderr)
    sys.exit(1)

interior = lines[1:-1]
dedented = []
for line in interior:
    if line.startswith("    "):
        dedented.append(line[4:])
    elif line.strip() == "":
        dedented.append(line)
    else:
        print(f"error: {path}: interior line not indented by 4: {line!r}",
              file=sys.stderr)
        sys.exit(1)

with open(path, "w", encoding="utf-8") as f:
    f.writelines(dedented)
```

## Fix manifest evaluation for cross-compile

The current manifest declares the `CZLib` system-library target inside
`#if !canImport(Compression)`. SwiftPM evaluates manifests with the
**host** compiler. On macOS hosts the Compression framework exists, so
the `#if` branch is never taken and `CZLib` is never declared. When
cross-compiling for Android from a macOS host the sources still
`import CZlib`, and the build fails with:

```
error: no such module 'CZlib'
```

This PR moves the per-platform decisions from manifest-time host
conditionals to build-time target conditionals:

- `.systemLibrary(name: "CZLib", …)` is declared unconditionally.
- The `ZIPFoundation` target's dependency on `CZLib` is wrapped in
  `.when(platforms: [.linux, .android, .windows, .openbsd])`.
- `cSettings`/`linkerSettings` for `_GNU_SOURCE` and `-lz` are
  similarly gated.

On Apple targets the `CZLib` declaration is dormant — there's no
`brew install zlib` requirement and the produced binary is unchanged.

### Tools-version bump

5.0 → 5.3, required for `Target.Dependency.target(name:condition:)`.
5.3 was released 2020-09 and is supported by every Swift toolchain
currently used by ZIPFoundation downstream consumers I can find.
